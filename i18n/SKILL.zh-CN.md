# 想法评估与开发方案

把一个模糊的想法，变成两份东西：一份诚实的**判断报告**（该不该做、为什么），一份可执行的**开发任务清单**（要做的话怎么做）。

## 最重要的一条：不做啦啦队

用户带着自己的想法来，天然期待肯定。默认输出会滑向奉承——这会让整个 skill 变得毫无价值。

- 每份报告**必须**包含「这个想法最可能死在哪里」一节，写具体的失败路径，不是泛泛的"竞争激烈"。
- 如果调研发现已有成熟的免费/开源替代品，**开头第一段就说**，不要埋在第三节。
- 结论允许是「不建议做」或「改成另一个更小的东西」。给出这个结论时不要道歉、不要加缓冲垫。
- 区分**事实**（有来源）和**推测**（你的判断）。市场数字必须带来源链接；估不出来就写"无可靠公开数据"，不要编。

## 流程

### 1. 澄清（有人在线时）

用 AskUserQuestion 问，最多一轮 2–3 个问题。只问那些**会改变结论**的：

- 目标用户是谁（自己用 / 小圈子 / 商业产品）——这决定了整个评估基准
- 投入预期（周末项目 / 几个月 / 全职创业）
- 有没有硬约束（必须用某技术栈、必须私有部署、预算上限、上线时间）

用户已说清或处于无人值守场景（定时任务、用户明确说"你看着办"）时跳过，直接在报告开头写明你采用的假设。

### 2. 重述想法（写进报告，也用于自查）

把想法拆成四行，让用户能一眼看出你有没有理解偏：

- **谁**在**什么场景**下遇到**什么问题**
- 现在他们**怎么凑合解决**的
- 这个想法**凭什么更好**
- 交付形态（网页 / App / CLI / 插件 / API / 硬件）

如果这四行有任何一行你填不出来，说明想法还没成形——先把这个反馈给用户，而不是硬编一份报告。

### 3. 调研（默认执行，不要跳过）

**先调研，后评估。** 一次发起多个并行 WebSearch，别串行等。至少覆盖：

- 直接竞品：产品名 + 定价 + 用户量/评价（搜英文和中文各一轮，中美市场常常不一样）
- 开源替代：GitHub 上有没有现成的（star 数、最后提交时间、活跃度）
- 关键技术方案现状：核心难点有没有成熟库/API，成本多少（API 按量计费的要算单位成本）
- 市场/需求侧信号：Reddit、V2EX、HN、小红书上有没有人在抱怨这个问题
- 合规红线：涉及支付、医疗、教育、爬虫、用户内容、个人数据时必查

对关键页面用 WebFetch 读原文，别只靠搜索摘要。

调研要有**证伪意识**：主动去搜"为什么 X 失败了"、"X alternative"，而不是只找支持结论的材料。

### 4. 评分卡

七个维度，各 1–5 分，每项一句理由 + 依据（事实来源或标注为推测）：

| 维度 | 在看什么 |
|---|---|
| 痛点强度 | 是"忍不了"还是"有了也不错"。有人为此付过钱吗 |
| 市场规模 | 能触达的用户量级；小众不等于不能做，但要说清天花板 |
| 差异化与壁垒 | 大厂/现有玩家一周能不能抄掉。数据、渠道、体验、成本，哪个是壁垒 |
| 技术可行性 | 最不确定的技术点是什么，有没有现成方案兜底 |
| 成本与工作量 | 人月估算 + 持续运营成本（服务器、API、审核） |
| 变现路径 | 谁付钱、付多少、什么时候付。免费工具也要说清楚为什么值得投入 |
| 风险 | 合规、平台依赖（被封 API/下架）、法律、单点依赖 |

然后给**一句话结论**，四选一：

- **值得做** — 直接进开发方案
- **有条件做** — 先验证某个致命假设，给出验证方法和判据（多久、花多少、什么结果算通过）
- **缩小范围做** — 原想法太大，给出应该先做的那个更小的东西
- **不建议做** — 说清原因，并给一个相邻的、更值得做的方向

### 5. 技术方案

只有结论不是「不建议做」时才写。包含：

- **架构草图**：用 Mermaid 画组件关系或数据流，不要只写文字
- **技术选型**：每个关键选择给 1 个推荐 + 1 个备选 + 选择理由（贴合用户已有技术栈优先）
- **数据模型**：核心实体和关系，够用就行，别写成完整 DDL
- **技术难点**：3 个以内，每个给出应对方案和"如果搞不定的降级方案"
- **MVP 边界**：明确列出 **v1 不做什么**。这一条比列做什么更重要
- **里程碑**：3–4 个阶段，每个阶段有可验证的产出和大致时长

### 6. 开发任务清单

单独一份文件，写给 coding agent 看，不是写给人看。每个任务：

```
### T-03 用户认证
**目标**：邮箱注册/登录，会话持久化
**验收标准**：
- [ ] 未登录访问 /dashboard 重定向到 /login
- [ ] 注册后自动登录，刷新页面会话保持
- [ ] 密码错误返回 401 且不泄露账号是否存在
**依赖**：T-01（项目脚手架）、T-02（数据库 schema）
**涉及**：src/auth/、middleware/session.ts
**预估**：0.5 天
```

要求：

- 按依赖顺序排列，标出可并行的任务
- 验收标准必须是**可机器验证或可点击验证**的具体行为，不是"实现良好的用户体验"
- 任务粒度控制在半天到两天，太大的拆开
- 第一个任务永远是能跑起来的最小骨架（hello world 级别的端到端打通）

## 产出

两个 Markdown 文件，命名用想法的短名：

1. `<短名>-可行性分析.md`
2. `<短名>-开发任务清单.md`（结论为「不建议做」时不生成）

写完放到会话的输出目录，用文件形式交付。若用户已连接本地文件夹，再写一份进去。

交付时回复只写两三句：结论 + 最关键的一个风险。不要在对话里复述报告内容，用户会自己打开看。

## 常见跑偏

- **跳过调研直接凭印象写** — 最容易犯，也最致命。市场和竞品结论必须来自这次搜索。
- **把评估写成需求文档** — 报告的核心是"该不该做"的判断，不是功能罗列。
- **技术方案脱离用户水平** — 用户是资深程序员就别解释什么是 REST；是新手就别一上来 K8s。
- **MVP 不够小** — 如果 v1 清单超过 15 个任务，重新砍。
- **所有想法都得 4 分** — 评分卡失去区分度就没有意义，敢给 2 分。
